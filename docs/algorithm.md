 任务连贯性 × 四路互斥路由算法

 一套让 AI 智能体「做完了才收」的提示词算法，与双通道发送的互斥路由规则

 
 提示词工程回合经济学路由互斥状态续跑
 

 

 
 摘要

 旧提示词把「聊天一句一收」的回合经济学套到「干活」上，导致智能体每完成一小步就结束回合，用户必须反复说「继续」。本算法不靠加大轮次上限，而是在核心提示词顶部加入最高优先级的任务连贯性总则：把结束回合的判据从「有没有话说」改成「目标有没有完成」。

 同时修复两条发送通道互相压过的问题——从「微信绝对优先」的打补丁思路，改为四路互斥：只有微信信号走微信直发，只有助理信号走助理转交，两个信号同时出现只反问，都没有就正常对话。

 后续全面复查定位出 14 个优化点：P0 五条留待人工判别，P1 六条与 P2 三条已全部落地，包括回合间续跑、转交前补全需求、语音错字容错、首发防线、上限收束、前缀瘦身、冗余自动核对与敏感内容首次确认。

 

 
 一 · 问题诊断

 1. 回合被切碎：一句话为什么要说三次

 四条规则互相提供「可以收了」的合法性：

 
 规则传达的暗示叠加后的后果

 一条消息一次汇报气泡，说完结束回合说一次 = 回合结束多步任务被切成一回合一步

 不描述打算做什么，不写内心判断中途不能旁白工具间隙既不能说话也不许沉默地继续

 沉默是正常的动作没话说就走被泛化到任务进行中

 没话可说就结束回合（系统级注入）再次强化收尾倾向与前一条叠加

 
 最关键的一点：原规则中没有一条反着说「目标没完成不许走」。模型在任意两个工具调用之间都有充分理由结束回合。

 2. 两条通道互相压过

 实测中「把你好发给微信文件传输助手」被连转 7 次助理转交、微信直发一次没调——转交规则压过微信直发；补「微信绝对优先」后，「提到助理」的请求又被微信抢走。单通道优先注定按下葫芦浮起瓢。

 3. 架构层放大器

 智能体是事件驱动的：每条语音是一个新事件帧（新回合）。回合内没有「目标未完成禁止结束」，回合间没有「主动续跑上次未完成目标」，回合一旦被切碎，续跑只能靠人嘴说。

 

 
 二 · 算法总览：两套经济学分开

 
 聊天场景：一句一收。没有新指令、只是被拖动被戳时，保持安静或只回半句。

 干活场景：做完了才收。目标未完成且还有可自主执行的下一步时，继续调工具，哪怕中间一句话都不说。

 是否结束回合，由目标状态决定，不由说没说话决定。

 
唤醒 → 形成目标 G
循环：
 若 G 已完成：一次完整汇报 → end_turn
 否则若缺只有主人才能给的信息：提问 → end_turn
 否则若命中需确认的对外动作：请求确认 → end_turn
 否则取下一步 next：
 若 next 存在：静默调用工具 → 回到循环
 若 next 不存在：说明阻塞原因 → end_turn
 

 
 三 · end_turn 三态判定

 
 状态判据动作反例

 目标完成要查的查完、要写的写完、要发的发出一次完整汇报后结束还有文件没写就说「弄好了」

 缺主人独有的信息确实缺一个只有本人能给的事实提问后结束能从上下文推断却停下来问

 命中需确认的对外动作对外发送 / 发布 / 删除，且对象不唯一请求确认后结束收件人和内容已确定还回头问

 
 口径：能从当前对话、已读文件、待办文件、工具返回的错误或候选里推出的，一律自己推，不问。只有确实缺事实才问。

 结束前自检：目标完成了吗？还有没有我能自己做的下一步？只要还有下一步，就继续做——「我这一步说完了」不是结束理由。

 

 
 四 · 四路互斥表（核心）

 两条发送通道只按用户话里的信号选，绝不混用，也不许一条压过另一条。三份提示词与两个工具描述共用这张表：

 
 话里的信号举例直接动作禁止动作

 只有微信信号微信 / 发微信 / 给谁发 / 告诉谁 / 转告 / 捎话微信直发工具不调转交工具、不转交、不写转交记录

 只有助理信号助理 / 唤醒助理 / 交给助理 / 让助理处理助理转交工具，只回固定确认句不调微信直发、不自行查资料、不复述需求

 两个信号同时出现「助理，把你好发给微信文件传输助手」只反问「直接用微信发，还是交给助理处理？」不猜、不默认、不两个都调

 都没有正常说话、提问、查资料正常对话或对应工具不调这两条发送工具

 
 信号判定看是不是在下达任务：关键词本身不作数，看这句话是不是命令。「给妈妈发个微信」是命令，命中；「微信怎么又崩了」是聊天提问，不命中。判一次就动手，不为一条信号反复权衡。

 
 只说「调用微信 / 继续」而上文有未发完的微信任务 → 沿用上一条已拆好的收件人与正文直接发送，不再问、不再转交。

 来源是助理的返回结果不算新指令，禁止再转回去；两者都有的先反问。

 转交失败时告诉用户失败原因，不改用本地搜索或自己执行。

 
 

 
 五 · 加固九项（P1 × 6 + P2 × 3）

 
 编号加固项

 P1-6回合间目标续跑：新回合无新指令时，先查待办文件里标「进行中」的条目接着干

 P1-7转交前先补全需求：依赖内部资料的转交先查知识库，结论写进转交内容，不甩「你自己去查」

 P1-8信号词语音错字容错：错字按发音判定信号（「助力」→助理、「维信」→微信），拿不准先确认

 P1-9首发防线：判错没有后悔药——判定必须做在调用之前，回执只兜底不兜首发

 P1-10接近回合上限先收束：约 40 步以上把结论与下一步写进待办再简短汇报结束

 P1-11混合句反问后的承接链路补进验证清单

 P2-12前缀瘦身：低频规则迁按需卡，核心前缀只留两条高压线，节省每轮 token

 P2-13冗余自动核对：脚本一次核对运行时与交付副本八处关键句，缺一处即报警

 P2-14敏感内容首次确认：金额 / 地址 / 承诺类正文先复述确认再发，日常消息直发

 
 

 
 六 · 验证清单（15 步，节选）

 
 多步任务全程不出现中途结束回合，不需要用户说「继续」

 两次工具调用之间没有汇报也继续调工具，不空转、不自言自语

 「给文件传输助手发条消息」→ 直接走微信直发，不转交

 「让助理处理一下」→ 直接走助理转交，只回固定确认句

 混合句「助理，把你好发给微信文件传输助手」→ 只反问，两个工具都不调

 「微信怎么又崩了」→ 正常聊天，不调任何发送工具

 助理回传「把 X 发给微信 Y」→ 直接微信直发，不再转回去

 语音说「助力，帮我处理下XX」（助理错字）→ 按发音判为助理信号

 长任务跑到约 40 步 → 触发收束：待办标「进行中 + 下一步」，新回合能续跑

 八 · 边界与红线

 
 收件人、内容、目标能唯一确定时直接执行；存在歧义、后果不可逆且对象不明确时才停下确认。
